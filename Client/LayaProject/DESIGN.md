# 客户端全局设计

本文件作用于整个 `Client/LayaProject`。子目录中的 `DESIGN.md` 自动继承本文件规则，并可在自身作用域内补充更具体的约束。

## 文档系统

项目知识按目录作用域组织，不建立与代码树脱离的第二套知识树。

- `README.md` 说明当前可用能力、公开入口和使用方法。
- `DESIGN.md` 说明架构、边界、稳定约束、设计取舍和重复错误的防范方式。
- `PlanAndStatus.md` 只保存当前未完成工作、优先级、阻塞和验收条件。
- 三类文件都可按需不存在。没有信息就不创建文件，也不保留占位章节。
- 外层 DESIGN 是后代目录的默认规则；内层 DESIGN 负责局部细化。
- 内层若需违反外层规则，必须明确写出“例外声明”、原因和影响，并在用户确认后才可实施。沉默偏离无效。

Plan 是工作面板，不是历史档案。工作完成后，公开结果归入 README，稳定决策和可复用教训归入 DESIGN，其余过程信息删除。Plan 清空后删除文件。

规则按实际使用演进：只在需求已确认、错误重复发生或现有约束不足时新增；当规则不再匹配代码时同步修订或删除。

## 工作约束演进

已确认的命名演进：对需要持续扩展的同一类型族，抽象或可复用父类使用 `Base<类型>`，其直接业务子类使用 `<类型><职责或状态>`。例如 `BaseState`、`StateIdle`、`StateRun`、`StateAttack`，以及更具体类型族中的 `BaseSceneState`、`SceneStateLoading`、`SceneStatePlaying`、`SceneStateResult`。这样同族实现会在编辑器的文件和符号列表中聚集，便于检索和审阅；该规则服务于类型族识别，不得为了字母排序而削弱已有领域语义或进行无收益的批量改名。

## 诊断日志标志头

- 临时诊断日志必须使用稳定、唯一且可搜索的标志头，格式为 `[DBG-<ISSUE_KEY>]`；同一问题的创建、状态变化、拒绝、成功和结束日志使用同一个标志头。
- 标志头用于按问题筛选日志、批量删除临时日志和后续关闭诊断输出；不要在同一问题中混用多个前缀。
- 模块常规业务日志可以使用现有模块前缀；只有诊断日志必须遵循 `[DBG-...]` 规则。

## 模块边界

`src/logic/` 与 `src/start/` 采用扁平模块设计：其下一般只保留一层模块目录，一个目录提供一项完整能力。

- 模块必须有明确、统一的对外入口，调用者不应依赖内部协作对象。
- 有全局生命周期的服务模块通常以 `XXXMgr` 或已有 Manager 类为入口，并实现 `IManager`。
- 算法、策略或能力型模块可以使用 Facade、Agent、Executor、Factory 等符合职责的入口，不强制制造 Manager。
- `Protocol` 只在模块确有网络消息时存在；`Data`、`Info` 和文档也都按需存在。
- 避免在模块内继续建立 `manager/service/model` 等无必要的分层目录。确有复杂度需要例外时，按文档例外流程确认。

## 运行边界

客户端分为启动层与逻辑层。

- `src/start/` 负责启动、加载、登录、网络和平台 SDK，并先于逻辑分包可用。
- `src/logic/` 负责游戏主体能力。逻辑层运行时不得反向静态导入 Start 实现，以免破坏分包边界；共享服务通过 `App`、窗口桥接或明确的类型契约取得。
- `src/logic/LogicMain.ts` 是逻辑层组合根：先初始化配置，再向 `ManagerHub` 注册需要统一生命周期的 Manager，随后统一初始化并驱动更新。
- `src/logic/App.ts` 是跨层服务访问入口，不负责注册 Manager。
- 全项目只保留 `src/start/loading/LoadingMgr` 一套 Loading 显示实现。LoadingMgr 负责界面显示、逐帧刷新与关闭；各调用模块通过回调自行提供显示文字、进度值和完成条件。Logic 不得通过 `UIManager` 再创建第二套 Loading 界面，也不得静态导入 Start 的实现类。
- `ManagerHub` 只注册需要统一生命周期协调的 Manager：需要统一 `init`、`reset`、`release` 或逐帧 `update` 中任一能力即可注册，各生命周期方法均为可选。无状态工具、纯算法和自行管理生命周期的服务不注册；不能为了满足接口保留空 `update`。新增注册时必须确认初始化依赖与反向释放顺序。

## 微信构建与分包

- 微信首包只保留启动场景、`startupUI` 和 `ttf`；Loading 背景属于 `startupUI`，不得通过 `alwaysIncluded` 强制打入整个大图目录。
- `logic` 是微信本地纯代码分包：`assets/logic/` 是分包资源锚点，构建路径为 `logic`；入口为 `src/logic/LogicLib.bundledef`，不得标记为远程包。不得把 `src/logic` 的源码路径填写到资源文件夹，否则微信分包会被发布到包体根目录之外。正式资源按现有顶层路径形成 `bigImg/character/config/effects/guides/map/scene/shaders/ui` 远程分包，以保持运行时 URL 不变。
- 代码动态加载的资源目录同时列入 `alwaysIncluded` 和对应的远程 `subpackages`：前者保证导出器不会裁剪资源，后者使它们输出到 `wxgame-remote` 而不是微信本地包。两个列表必须与 `MyGameConfig.remoteResourcePackages` 同步。
- 所有游戏分包关闭构建器的启动前自动加载。首包 Loading 先注册微信本地 `logic` 代码包；资源包地址选择只能由 `MyGameConfig.resourcePackageBaseUrl` 决定：IDE 预览调用本地 `loadPackage(name)`，发布产物（包括微信开发者工具）调用远程 `loadPackage(name, remoteUrl)`。LogicMain、ConfigMgr 和 UIManager 只能在全部分包注册后初始化。
- `MyGameConfig` 由 Start 首包拥有，统一选择环境、登录 API、远程资源地址和仅限开发环境的 Gateway 兜底。Start 在加载 Logic 前向 `window.myGameConfig` 发布不可变快照；Logic 只能通过 `App.gameConfig` 和 type-only 契约读取，不得静态导入 Start 配置实现。正常 Gateway 地址继续以登录服务器返回值为权威来源。
- 平台 SDK 与认证环境不得通过组合子类交叉膨胀：`WechatMiniGameSDK` 负责微信平台 API，`MyGameConfig.loginMode` 决定开发凭据或真实微信凭据。开发微信凭据只能用于 `Local`；`Test`/`Production` 必须使用 `wx.login`，且服务端 Production 必须执行真实平台验证。
- `Local` 允许 HTTP/WS 以支持本机和局域网联调；`Production` 的登录 API 与远程资源地址必须为 HTTPS，且不得设置 Gateway 兜底。微信开发者工具中的本地发布测试与 IDE 预览不是同一加载模式，不得用 `LayaEnv.isPreview` 以外的零散条件在业务代码中重复判断。
- `assets/testAndSample/` 下脚本集必须关闭 `allowLoadInRuntime`。正式构建后必须同时检查资源清单和 JS bundle；只确认测试场景未导出不足以证明测试代码已排除。
- 微信移动端纹理默认在 Android 与 iOS 统一使用 `ASTC_6X6`，PC 开发环境显式使用 `R8G8B8A8`，不得让启用默认压缩后的 PC 格式隐式落入 BC1。非自动图集图片的目录策略由 `settings/plugin-JFrameworkTextureImportRules.json` 和 `src/editor/textureImport/` 的导入处理器统一维护，`.meta` 只是导入结果，不是人工配置入口。`startupUI` 和 `ui` 中真正符合纹理类型、递归范围与单图尺寸上限的精灵由各自 `.atlascfg` 处理；角色与特效的手工 `.atlas` 纹理、大地图以及超过图集上限的 UI 散图继续由目录导入规则处理，不得为了套用目录规则再次打成自动图集。
- 发布配置必须开启压缩纹理。当前保留 PNG/JPG 源图作为开发者工具和不支持 ASTC 设备的兼容回退；只有完成目标真机覆盖验证后，才能为了包体关闭源图保留。普通 IDE 预览不用于判断 ASTC 是否生效，发布后以 `fileconfig.json`、生成的 KTX 文件和真机网络请求为准。
- `assets/config/*.json` 属于数据资源并进入 `config` 分包，不参与 ASTC 纹理压缩；其输入和生成约束继续遵循“配置输入与生成物”。

## 数据命名

- `XXXData` 只包含 `number`、`string`、`boolean` 等基础字段，不包含数组、嵌套对象和业务方法，适合传输与直接序列化。
- 含数组、嵌套对象、引擎对象或业务方法的数据结构使用 `XXXInfo` 或更准确的领域名称。
- 不为满足命名格式创建无意义的 Data/Info 类。

## 配置输入与生成物

- `Config/csv/*.csv` 是静态配置的唯一人工编辑入口。客户端 JSON、manifest、服务器 JSON 和 Java 配置类必须由配置导出工具产生，不得手工修改生成物。
- 新增或修改配置前先定义输入端：字段名、类型、说明、`UsedSize`、ID、空值语义、枚举范围以及颜色、路径等字符串格式；不能先改 JSON 或 Java 再反推 CSV。
- 仅客户端使用的配置字段标记为 `c`，仅服务器使用的字段标记为 `s`，双端字段标记为 `cs`。客户端专用表不要求生成 Java 类。
- 修改 CSV 后必须重新运行对应导出器，并同步验证生成 JSON、manifest 和实际消费端。

## 精确整数

- `playerId`、经验、货币以及其他可能超过 `Number.MAX_SAFE_INTEGER` 的协议字段使用十进制字符串，不得直接声明为 `number`。
- 精确计算统一使用 `src/logic/common/ExactInteger.ts` 的规范化与 `bigint` 能力。UI 仅将安全的小余数、比例或已格式化文本转换为普通数字。
- 数量被业务上限明确限制在安全整数范围内时可以使用 `number`，但服务端必须执行同一上限校验。

## 独立 UI 设计与美术拼装流程

本节适用于新建完整界面、弹窗、HUD、结果页以及需要整体重做的 UI，不限于某个业务模块。

1. **先定义设计契约。** 开始生产前明确界面用途、UI 层级、设计画布、安全区、逻辑占用范围、信息内容、交互、数据来源、目标模块和最终资源目录。
2. **区分结构参考与风格参考。** 用户提供的截图默认只说明组件种类、信息层级和摆放关系；只有用户明确确认时才继承其美术风格。每次收到 UI 参考图后，在设计或生成任何美术资源前，必须先将其配色、材质、轮廓、描边、明暗关系与 `docs/ArtResourceGuide.md` 的锁定风格逐项比对，并明确记录结论：风格一致时可同时作为结构和风格参考；风格不一致时只能作为结构/样式参考，正式资源继续遵循项目锁定风格，不得混入参考图的材质或色调。开始独立 UI 设计前，必须先读取 `docs/ui-references/` 中与宿主场景或目标模块匹配的已确认参考图；若不存在匹配参考，必须向用户索取主界面或目标场景截图，不得自行假定风格。设计说明中必须分别写明结构来源、风格比对结论与项目风格来源。
3. **先审整屏，再审零件。** 正式资源生产前必须在完整目标画布或真实页面截图上完成包含背景、主视觉、标题、信息区、按钮及关键状态的整屏概念稿，并确认层级、密度、配色、占用比例和安全边距。孤立组件好看不能替代整屏确认。
4. **复用由适配性决定。** 审计 Common 和模块资源后，只有语义、状态、轮廓、材质、边框重量、色温、目标尺寸与整屏效果都匹配时才复用；不得为了减少文件而用近似资源拼凑正式界面。只服务单个界面的资源留在模块内，至少两个界面具有相同语义和缩放契约时才提升为 Common。
5. **按行为拆分资源。** 固定图标和装饰使用独立图片；可拉伸面板、标题条和按钮先决定九宫格；先区分固定结构与数据重复结构：数量可变、同构展示行、可由数据排序/筛选或需要统一绑定交互的内容，使用 `GList` 加独立 `.lh` item，并由 `itemRenderer + numItems` 绑定；当 item 数量可能超过可视区域时，必须同时设置 `clipping` 并挂载与布局同方向的 `Laya.Scroller`，验证拖拽、回弹和初始滚动位置；仅有固定数量且语义、布局或交互各异的节点保持显式节点，不为形式强行列表化。标题、说明、评分、数量、百分比等动态内容由 Laya 文字与数据节点承载；Controller 只负责状态、数据和交互，不用运行时绘图替代正式美术。
6. **按运行尺寸生产。** 资源表必须同时记录逻辑显示尺寸、源图尺寸、透明度、九宫格、最终路径和状态。正式图片像素应接近实际显示尺寸，生成器大图必须裁切、清除多余透明区并缩放后才能入库，不能直接缩小塞进页面。
7. **直接进入规范目录。** UI 模块的 `.ls`、`.lh` 和作用域文档放在模块目录；模块专用 PNG 从生成清单开始就输出到其 `imgs/` 子目录，公共图片输出到 `assets/ui/common/imgs/`。`assets/` 内不保留概念稿、生产图集、对比图或临时切片。
8. **使用真实导入关系拼装。** 新图片必须由 LayaAir IDE 生成 `.meta` 和 UUID，取得真实 UUID 后才能写入 `.ls/.lh` 的 `res://`；已有图片迁移时 PNG 与 `.meta` 必须成对移动并保持 UUID。固定本地美术、色块、边框和遮罩使用 `GImage`，不能用空 `GTextField` 冒充背景或图片节点；`GBox` 仅用于没有视觉职责的布局或分组，不能代替图片节点。纯色视觉面统一复用公共纯色九宫资源，在 `.ls/.lh` 声明，禁止 Controller 临时绘制。
9. **在真实上下文验收。** 拼装后检查图片尺寸与透明度、九宫格、UUID 引用、文字样式、JSON 和 TypeScript；最终必须在 LayaAir IDE 或目标设备查看完整界面，验证适配、交互层、Controller 状态和视觉统一，再根据整屏截图完成一次针对性修正。

**页面底面选择。** 全屏美术背景只用于 Loading、登录、地图或确有独立场景叙事的页面；普通功能页、弹窗、结算页和信息面板默认保留其宿主场景，仅使用输入遮罩和局部承载面板。底面能用纯色或低细节填充时不得额外生成花哨背景；可拉伸的标题条、按钮和面板优先使用已验证的九宫格资源。

**界面适配。** 先按设计画布完成视觉层级，再为每个根级节点选择明确的 Relation：全屏遮罩或背景绑定根节点宽高；固定尺寸的主视觉、标题、信息面板和主操作以根节点横向中心、纵向中线为锚点，使画布比例变化时整体平移而不拉伸或挤压；面板内部元素仅绑定其直接父容器，保持已确认的相对节奏。不得把所有节点盲目拉伸到全屏；安全区、顶部 HUD 或底部导航有明确依附语义时，改用相应边缘 Relation 并在真实设备验收后固化。

**主界面内页层级。** 背包、征战等需要保留主界面顶部 HUD 和底部导航的内页使用 `UILayer.MainContent`（`zOrder=90`），低于 `MainUI` 壳层（`zOrder=100`），不得使用 `UIWindow` 弹窗层。内页的可交互内容只能位于当前主界面 HUD 与底部导航之间的安全区域；主界面壳层继续负责其自身的显示和点击，避免内页被 HUD/导航遮住或反向拦截导航。

主导航离开当前内页、切回主世界或切换场景前，必须通过 `UIManager.closeLayer("MainContent")` 关闭该层页面；不能依赖目标路由恰好与当前页面配置了互斥关系。打开同一内页时可以按名称保留自身，避免无意义地关闭后重开。

**主界面内页承托与窗口。** 当内页不能透出宿主场景时，在 `MainContent` 内先放置非交互的低细节灰蓝承托底面，并使用根节点宽高 Relation 覆盖画布；它仍位于 `MainUI` 下方，因此 HUD 和底部导航保持可见。功能窗口作为其上的暖色/金色边框面板，面板和可滚动物品区各自用已确认的根节点 Relation 适配画布。不要用灰蓝底面替换窗口本身，也不要让城墙等宿主场景从窗口周边或内容区漏出。

**同组页签。** 同一页签组的点击热区、可见尺寸和基线必须固定一致；选中态只切换已导入的背景资源、文字或主题色，不得通过位移、缩放或挤压相邻项来表达。需要在控制器中切换的固定本地页签图允许使用 `GLoader`，但 `.ls` 必须同时声明初始 `src`，保证 LayaAir IDE 预览与运行时首帧一致；资源导入后保留 IDE 生成的 `.meta`。

以下做法视为已确认的错误：未确认整屏就逐个拼组件；把参考布局误当参考风格；让通用面板反向决定信息层级；把生成器大图直接缩放使用；为了复用混入不同材质或色温；把动态文字烘焙进 PNG；用 `GTextField` 或 Controller 绘图代替正式背景；把 PNG 放在 UI 模块根目录；手写 `.meta` 或猜测 UUID；只通过静态检查就宣布界面完成。

## LayaAir 3.3 约束

- 运行时资源路径相对 `assets/` 根，例如 `startupUI/login/Login.lh`，不得写成 `assets/startupUI/login/Login.lh`。
- 新 UI 序列化节点使用 LayaAir 3.3 对应的 `GBox`、`GImage`、`GTextInput` 等类型；修改 `.ls/.lh` 前先核对同项目的有效文件。
- 固定本地图片使用 `GImage`；只有业务代码确实会更换图片来源、需要异步/远程加载或依赖 fit/align 行为时使用 `GLoader`。不得因为初始化代码重复写入同一个固定 URL 而保留 GLoader。
- 承担点击语义的控件使用 `GButton`，固定背景和图标作为其 `GImage` 子节点，动态业务图标才使用 `GLoader` 子节点；普通装饰图片不为了形式包装成按钮。
- GButton 的按下反馈以中心缩小为默认行为，常规按钮缩放到 `0.92`，紧凑图标按钮可缩放到 `0.9`；节点必须使用中心锚点或等价状态配置，避免缩放时向单侧漂移。点击音效配置在 GButton 的 `sound` 能力或未来统一按钮行为层，不在图片节点上分散监听。
- 页签和主导航的选中态用于表达当前位置，不套用普通按钮的持续缩小状态；选中项可以在不挤压相邻项的前提下从中心放大约 `1.08`，并使用比未选中项更醒目的主题强调色。若 `GButton` 使用 Radio/Check 模式，必须核对引擎的 `Down` 页同时承担选中常态，避免把选中页误配为 `0.92`。
- 只有出现跨界面复用的完整视觉结构、统一防连点、长按、冷却或红点等复合能力时才建立公共 Button prefab/行为组件；单个界面内的普通按钮直接使用 GButton，不重复实现按钮状态机。
- 美术资源复用、独立 UI 的生产门禁和模块图片目录遵循上方“独立 UI 设计与美术拼装流程”；没有合适资源时新增正式 PNG，不以近似资源拼凑。
- `.meta` 文件及 UUID 必须由 LayaAir IDE 创建；对于 IDE 已生成的 `.meta`，只有在项目内存在同版本真实样本且字段语义已确认时，才可维护 `importer` 中的确定性导入设置，例如九宫格 `sizeGrid`。不得修改 UUID、猜测未知字段或以手工文件代替 IDE 首次导入，修改后必须回到 IDE 验证。
- 代码创建输入框使用 `new Laya.Input()`；不存在 `new Laya.TextInput()`。
- `.ls` 用于场景，`.lh` 用于可复用层级或预制体。资源引用保留 Laya 生成的 `res://` 关系。
- 不手工伪造资源或 UI 的 `.meta` 文件。需要导入和生成元数据时交给 LayaAir IDE。
- UI、场景和资源行为不能只凭 TypeScript 检查判定完成；涉及引擎序列化或生命周期时还需在 LayaAir IDE 中实测。

## UI 文字样式

- 客户端维护 `Config/csv/UITextStyle.csv` 作为语义化文字样式的唯一输入，不与服务器协议或玩法配置混用；运行时只读取工具生成的 `assets/config/UITextStyle.json`。
- 样式以使用场景命名，例如页面标题、面板标题、正文、按钮、说明、数值、伤害值和胜负结果，不以具体节点名或页面类名命名。
- “拼界面”时必须先查阅并复用样式中的字体、字号、颜色、粗体、描边像素、描边颜色和对齐约束；只有确有独特语义的文字才允许局部覆盖，并说明原因。
- 颜色输入统一使用 `#rrggbb` 十六进制字符串，不在 CSV 中混用 `rgba(...)`；`Stroke=0` 表示无描边，`Stroke>0` 时必须提供 `StrokeColor`。
- 序列化 `.ls/.lh` 在 LayaAir IDE 中按 CSV 样式值拼装；运行时创建或需要切换状态的文字使用 `UITextStyle.apply()`，不在 TypeScript 中复制颜色和描边常量。
- 样式配置只提供视觉规范，不负责文案内容、本地化文本或服务器状态。

## 文本编码与换行

所有项目自有文本文件强制使用 **UTF-8 无 BOM** 和 **LF** 换行。

- 不允许 UTF-8 BOM、GBK、ANSI 或其他本地编码进入仓库。
- 不允许 CRLF 与 LF 混用；Windows 开发环境同样保存为 LF。
- `.editorconfig` 约束编辑器保存格式，`.gitattributes` 覆盖个人 Git 的 `core.autocrlf` 差异。
- 修改含中文的文件后必须运行文本格式校验。发现乱码时停止继续编辑，先从 Git 或可信来源恢复原文，不能在乱码内容上猜测修补。
- 引擎资源、图片、字体和 Laya 自动生成的 `.meta` 不适用本规则，保持生成工具原样；我们会主动维护的 `.ls/.lh` 仍按文本规则执行。

## 高频错误防范

- 加载 404：先检查路径是否错误带有 `assets/` 前缀。
- `missing node type`：检查 `.ls/.lh` 是否混入旧版组件类型。
- 构造函数不存在：先核对 LayaAir 3.3 API 和项目内现有用法。
- Timer 残留：需要释放的 `Laya.timer` 任务必须使用稳定的函数引用注册和清理；重复初始化前先清理同一回调，不使用无法匹配释放的匿名回调。
- 场景切换必须由 `SceneMgr` 串行执行完整的退出、创建、进入和 UI 打开流程；按钮防连点只能减少请求，不能替代切换层的并发保护。销毁当前活动场景前必须先调用 `onExit()`，让子类解除舞台事件和异步令牌。
- Manager 未初始化：检查 `LogicMain.ts` 的注册顺序，而不是向 `App.ts` 添加注册逻辑。
- 文档与实现冲突：以源码和可验证运行结果修正文档，不能让过时文档反向约束当前事实。
