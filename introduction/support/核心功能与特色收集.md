### 1.3 协议代码自动生成

```yaml
# Protocol/message-ids.yaml（唯一真相源）
BAG_OPEN: 4001
BAG_CLOSE: 4002
```

运行 `npm run generate` 后自动同步生成：
- **TypeScript**：`MessageIds.ts`（客户端）
- **Java**：`MessageIds.java`（服务器端）

**价值**：避免前后端消息ID不一致导致的联调成本，新增消息只需改一处。

## 三、消息协议设计亮点

### 3.1 四层协议结构

```
Layer 1: Transport Header (24 bytes)  — playerId + serverId + gateId + timestamp
Layer 2: Message Header (2 bytes)     — msgId
Layer 3: Message Body (变长)          — 业务数据 JSON/Protobuf
Layer 4: Signature (32 bytes)         — HMAC-SHA256 签名
```

### 3.2 职责分离

- **Gateway**：只读取 26 bytes（Header），零拷贝转发，延迟 < 0.05ms
- **Game Server**：完整解析、验证签名、处理业务

### 3.3 消息ID编号规则

| 范围 | 分类 | 说明 |
|------|------|------|
| 101-199 | Start包硬编码 | LOGIN, LOGIN_SUCCESS, LOGIN_FAILED |
| 1000-1999 | 认证类 | AUTH, AUTH_SUCCESS |
| 2000-2999 | 心跳类 | HEARTBEAT |
| 3000-3999 | 游戏逻辑类 | GET_PLAYER_INFO, PLAYER_MOVE |
| 5000-5999 | 背包类 | INVENTORY_GET, ITEM_USE |
| 9000-9999 | 系统类 | ERROR, KICK, NOTIFICATION |

## 四、服务器线程模型（Game Server）

采用 **三线程池架构**，实现网络I/O与业务逻辑分离：

```
【1. Netty I/O 线程池】
  - Boss线程: 1个 (连接管理)
  - Worker线程: CPU*2 (网络收发)

【2. 消息队列】(LinkedBlockingQueue)
  - 接收队列: I/O线程 → 业务线程
  - 发送队列: 业务线程 → 独立发送线程
  - 容量: 10000

【3. 业务处理线程池】
  - 核心线程: 20
  - 最大线程: 100
  - 队列容量: 2000

【4. 独立发送线程】
  - 每个 Gateway 一个独立发送线程
```

**好处**：
- I/O线程专注网络收发，不被业务逻辑阻塞
- 业务线程专注逻辑处理，不被网络延迟影响
- 独立发送线程避免发送操作阻塞业务逻辑
- 消息队列平滑流量峰值

## 五、为什么选择 Laya 3.3？

1. **技术栈演进**：Laya 3.3 内置大量工具（Tile Map、UI 系统），设计逻辑向 Fairy GUI 靠拢
2. **AI 驱动未来**：现代游戏开发中 AI 已能承担超过 50% 的代码编写工作
3. **代码功能完善**：Laya 2 时代需要大量自研工具，Laya 3.3 已内置这些功能
4. **蓝图系统**：顺应降低技术门槛的行业趋势
5. **2D 游戏优化**：2D 摄像机、UI 系统强化，符合"2D 游戏用 Laya"定位
