## 二、系统架构

### 2.1 整体架构图

```
客户端 (Browser/微信小游戏/H5/App)
    ↓ WebSocket (JSON)
Gateway Server (8082) —— WebSocket 网关入口
    ↓ WebSocket (JSON) ⭐ 长连接 [Gateway→Game]
Game Server (8084) —— 游戏逻辑服务
    ↓ Redis (实时) + MySQL (持久化)
    ↓ HTTP REST (心跳)
Central Data Server (8083) —— 服务注册中心
    ↑ HTTP
Login Server (8081) —— 登录认证服务
```

### 2.2 服务器集群组件

| 服务 | 端口 | 职责 | 状态 |
|------|------|------|------|
| Login Server | 8081 | HTTP 登录认证，JWT Token 生成，第三方登录集成 | 已完成 |
| Gateway Server | 8082 | WebSocket 连接入口，三要素认证，消息路由转发，负载均衡 | 已完成 |
| Central Data Server | 8083 | 用户数据管理，会话管理，Gateway 分配与负载均衡，服务注册发现 | 已完成 |
| Game Server | 8084 | 游戏逻辑处理，状态同步，房间管理，消息路由 | 已完成 |
| Database Server | - | 数据库抽象层（预留） | 计划中 |

### 2.3 客户端架构（ManagerHub 模式）

```
src/
├── core/                    # 核心基础设施
│   ├── IManager.ts          # Manager 统一接口
│   ├── ManagerHub.ts        # Manager 统一管理中枢
│   └── Protocol.ts          # 消息处理基类
│
├── start/                   # 启动模块
│   ├── network/             # 网络模块
│   │   ├── NetworkManager.ts      # 网络管理器
│   │   └── MessageDispatcher.ts   # 消息分发器
│   └── login/               # 登录模块
│       ├── LoginMgr.ts
│       └── LoginProtocol.ts
│
└── logic/                   # 游戏逻辑模块
    ├── common/
    │   └── MessageIds.ts    # 消息ID定义
    ├── player/              # 玩家模块
    ├── bag/                 # 背包模块
    └── resource/            # 资源管理模块
```

**核心理念**：
- 单一职责：每个 Manager 只负责一个功能模块
- 统一入口：每个模块通过 XXXMgr 对外提供服务
- 生命周期管理：通过 ManagerHub 统一管理所有 Manager（init / update / reset / release）
- 消息驱动：网络消息通过 Protocol 处理，与业务逻辑分离

### 2.4 通信架构

**客户端 → Gateway → Game Server 链路**：

```
[客户端] → WebSocket → [Gateway]
                           ↓ WebSocket (JSON)
                       [Game Server]
                           ↓
                       [Redis / MySQL]
```

**关键设计决策**：
- **连接方向**：Gateway 作为 WebSocket 客户端主动连接 Game Server（扩容更灵活）
- **协议格式**：JSON（开发效率高，调试友好，内网性能足够）
- **服务发现**：Central Server 协调，推送式服务发现

### 2.5 心跳与服务注册机制

- **双重保障**：优雅关闭主动注销（延迟 < 3秒）+ 心跳超时检测兜底（延迟 15秒）
- **推送式发现**：Game Server 注册后 Central 立即通知所有 Gateway
- **心跳配置**：5秒心跳 + 15秒超时（行业标准）

## 三、命名规范与代码规范

### 3.1 Data vs Info 命名规范

| 条件 | Data | Info |
|------|------|------|
| 只有原始类型 | 适用 | 不适用 |
| 包含类成员/数组 | 不适用 | 适用 |
| 需要方法 | 不适用 | 适用 |
| 用于网络传输 | 适用 | 不适用 |
| 表示游戏实体 | 不适用 | 适用 |

### 3.2 三层 ID 体系

```
用户账号（Account）
    userId: "guest_1761815046402"
        │
        ├── 角色1  playerId: "player_12345"
        │            └── 会话1  sessionId (PC端)
        │            └── 会话2  sessionId (手机端)
        ├── 角色2  playerId: "player_12346"
        └── 角色3  playerId: "player_12347"
```

- **userId**：账号级操作（充值、封号、VIP）
- **playerId**：游戏业务逻辑（背包、战斗、社交）
- **sessionId**：连接级路由（精准消息推送、断线重连）

## 四、安全架构

| 安全机制 | 实现 | 说明 |
|----------|------|------|
| JWT Token 认证 | Login Server 颁发 | 无状态身份验证 |
| 三要素验证 | userId + loginTimestamp + token | 防重放攻击 |
| 网关分配验证 | 30秒超时连接机制 | 防止 Token 盗用 |
| 输入参数验证 | 完整请求校验和清洗 | 防止注入攻击 |
| 日志脱敏 | 敏感信息不记录 | 隐私保护 |
| 配置文件加密 | AES-256 + gzip | 防止数据泄露 |
| 签名验证 | HMAC-SHA256 | 消息防篡改 |
